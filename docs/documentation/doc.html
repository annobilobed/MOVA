Project summary

MOVA replaces queues and cash for UCC student bus travel. A student finds a trip, chooses an exact seat, pays digitally in Ghana cedis, and boards with a QR ticket that the driver of the assigned bus scans once.

What was built

Web application

Next.js 15 website: public landing page, trip search, seat selection, checkout, payment status, QR tickets, student dashboard, driver scanner, operator portal and super-admin area. Light and dark themes.

API

Node.js + Express + TypeScript service with PostgreSQL and Redis. Handles accounts, trips, ten-minute seat holds, Paystack payments, idempotent webhooks, tickets, validation, manifests and administration.

Tests

18 automated API tests covering the specification's acceptance criteria, plus a 19-step end-to-end browser run across all four roles.

Clickable demo and tour

A self-contained interactive demo (sample data) and a screen-by-screen tour, both viewable without a server.

Scope decisions

  • Built from scratch as a full web application. The Flutter mobile app described in the source specification is deferred.
  • Students register with any email address plus their UCC student ID.
  • Development data uses Cape Coast (UCC) as the origin with demo routes, all clearly labelled "Demo data".
  • Light and dark themes are included in the first release.
  • Visual direction: the mobility category standard executed at the level of Uber/Bolt, FlixBus/Omio and Revolut/Monzo.

The booking journey

1 DiscoverSearch trips
2 CompareFare, time, seats left
3 SelectChoose a seat
4 HoldServer holds it 10 min
5 PayPaystack, Pending
6 ConfirmBooking + QR ticket
7 BoardDriver scans once

Step by step

  1. Search. The student enters origin, destination and an optional date. Only upcoming, non-cancelled trips are returned.
  2. Choose a seat. The seat map shows each seat as Available, Your seat, Temporarily unavailable (held by another student) or Booked — always with a text label or icon, never colour alone. The map refreshes every 15 seconds.
  3. Hold. Tapping a seat asks the server to lock it in Redis for 10 minutes. The countdown appears only after the server confirms. Choosing another seat releases the first.
  4. Checkout. The student picks luggage. The server calculates the total (fare + luggage fee) and creates a Pending payment. Any amount sent by the browser is ignored.
  5. Pay. The student is redirected to Paystack (or the labelled test checkout). Re-trying within 15 minutes reuses the same open payment instead of creating another.
  6. Confirm. When Paystack confirms (via signed webhook or verification), the server creates exactly one booking and a unique ticket token, then releases the hold. The ticket appears only after this.
  7. Board. The driver scans the QR. The ticket is accepted once, only for the trip on the driver's assigned bus.

Payment outcomes

StateMessage to the studentWhat happens
Pending"We're confirming your payment."Page polls every 2.5 s; warns after 45 s that mobile money can take a minute
Successful"Your booking is confirmed."Ticket revealed with animation; link to My tickets
Failed"Payment wasn't completed."Shows whether the seat is still held; safe retry
Refunded"Your payment was refunded."Seat was taken before payment completed; refund issued
Needs review (flagged)"We're reviewing this payment."Amount/currency mismatch; no ticket; support path
Offline / timeout"Connection interrupted."Re-checks on reconnect; never assumes failure

How a request flows

The browser only talks to the website's own address. Requests to /api/* are forwarded by Next.js to the Express API, so the session cookie stays httpOnly and same-origin and is never readable by JavaScript. Public pages (the home page's live trips) are fetched on the server and refreshed every 30 seconds.

Data model

Defined in apps/api/src/db/migrations/001_init.sql. All IDs are UUIDs.

TableKey columnsPurpose and rules
companiesname (unique), is_demoTransport operators. Operators and drivers belong to one.
usersfull_name, email (unique, case-insensitive), phone, student_id, password_hash, role, company_id, is_activeRoles: student, driver, operator, super_admin. Passwords hashed with bcrypt.
busescompany_id, plate (unique), capacity (1–90), layout (JSON), driver_idLayout is an array of rows; each cell is a seat number or empty (aisle).
tripscompany_id, bus_id, origin, destination, departure_at, fare_pesewas, trip_type, is_cancelled, is_demotrip_type: inter_regional or campus_shuttle. Past departures cannot be created or booked.
paymentsreference (unique), user_id, trip_id, seat_number, luggage, fare/luggage/amount in pesewas, status, status_reason, provider, authorization_url, paid_atStatus: pending, successful, failed, refunded, flagged. Amounts always calculated by the server.
bookingstrip_id, user_id, payment_id (unique), seat_number, luggage, qr_token (unique), status, boarded_at, boarded_byUnique index on (trip_id, seat_number) for active bookings — the database itself prevents double booking.
webhook_eventsprovider, event, reference, received_atLog of every verified webhook received.
audit_logactor_id, action, target, details (JSON)Role changes, staff and company creation, failed refunds.

Seat locks (Redis, not the database)

mova:lock:{tripId}:{seat} → student ID, expires after SEAT_LOCK_SECONDS (600). mova:userlock:{tripId}:{userId} → the seat that student holds, so taking a new seat releases the old one. Seat availability = layout minus active bookings minus active locks.

Business rules

Every rule below is enforced on the server, and the starred ones are covered by automated tests.

#RuleHow it is enforced
1One active booking per trip and seat ★Unique partial index on bookings; insert inside a transaction
2A seat hold lasts ten minutes ★Redis key with 600 s expiry; set only if free (NX)
3A booking is created only after Paystack confirms ★Booking insert happens only in finalizePayment on a verified success
4The server calculates every amount ★Client amounts ignored; fare from the trip, fee from the luggage table
5Amounts in GHS; Paystack receives pesewasAll money stored as integer pesewas
6Duplicate webhooks never create duplicate bookings ★Payment row locked FOR UPDATE; only a pending payment can change
7Every successful payment ends in a booking or a refund ★If the seat is taken or held by someone else, the payment is refunded
8Wrong amount or currency is flagged, not booked ★Status "flagged"; admin overview shows the count
9A driver validates only tickets for their assigned bus ★Trip must belong to the driver's bus; mismatches return "wrong bus"
10A ticket is accepted once ★Atomic update from confirmed to boarded
11Operators see only their own company ★Company scope applied to every operator query
12Past trips cannot be created or booked ★Checked on trip creation, seat lock and payment start
13A student has at most one seat per tripLock refused if the student already has an active booking on the trip
14Every ticket includes 25 kg of luggage (3 kg margin); extra bags are paid per bag ★Server-side fees; top-ups charge only the difference and can never lower an allowance

Navigation

Public pages use a top navigation. Signed-in areas use a side navigation on desktop and a bottom bar on phones. Links a role cannot use are hidden, and any page opened by the wrong role shows a clear "not available for your account" message.

Responsive and accessible

  • Mobile-first layouts tested at 390 px phones and 1280–1440 px desktops.
  • Labelled inputs with errors next to the field; visible focus rings; keyboard-reachable controls; skip link.
  • Seat and payment states always carry text or icons, never colour alone; ticket details shown as text beside the QR.
  • All animation stops under the device's reduce-motion setting.

Deployment

Real website — Render

render.yaml creates, on free plans in the Frankfurt region: one web service running both the website and the API, a PostgreSQL database and a Redis store. Demo data is seeded on start and refreshed when all demo trips have departed.

  1. Create a Render account at render.com using "Sign up with GitHub".
  2. Open render.com/deploy?repo=https://github.com/annobilobed/MOVA; allow access to the repository if asked.
  3. Name the blueprint mova; leave PAYSTACK_SECRET_KEY empty for test mode.
  4. Click Apply. After 5–10 minutes the service shows "Live" and a link like https://mova-xxxx.onrender.com.
Free plan limitsThe service sleeps after 15 minutes without visitors (the next visit takes about a minute). The free database expires after 30 days. For launch, move to paid plans with daily backups, as the specification requires.

Clickable demo — GitHub Pages

Served from the /docs folder of the main branch at annobilobed.github.io/MOVA. The tour is at /tour/. The demo uses sample data and saves nothing.

Custom domain plan

  • yourdomain.com → the real website on Render (add the domain in the Render service settings, then the DNS records Render shows).
  • demo.yourdomain.com → the demo on GitHub Pages (CNAME record to annobilobed.github.io, then enter it in Pages settings and enable HTTPS).

Going live with real payments

  1. Add the Paystack secret key in Render's environment settings and remove ALLOW_TEST_PAYMENTS.
  2. In the Paystack dashboard set the webhook URL to https://yourdomain.com/api/webhooks/paystack.
  3. Run test payments end to end, including a duplicate webhook and a refund.
